# Issue #6 verification evidence

Implementation remains a modular monolith: polling only enqueues durable outbox work; `NotificationOutboxDispatcherService` runs on its own schedule. The broad agent rewrite of `PollingService` was rejected and preserved at `runs/factory-issue-6/evidence/PollingService-rejected.java`; production polling was restored from the worktree base before the narrow change.

- Full command: `./mvnw.cmd -B -ntp verify` with Temurin 17.0.20.1.
- Latest result: 223 tests, 0 failures, 0 errors, 2 skipped; Maven `BUILD SUCCESS`. Machine-readable Surefire summaries are in `target/surefire-reports`; captured command output is `runs/factory-issue-6/evidence/mvn-verify-deadline-fix4.log`.
- The two skipped PostgreSQL Testcontainers tests still block Factory release verification because Docker Engine is unavailable.
- Focused async-flow tests prove polling leaves the outbox pending without calling Telegram; an explicit dispatcher invocation then sends or records failure and keeps retries in the outbox. Existing Riot lock, pagination, rate-limit handling, caching, filters, metrics and error mapping remain in `PollingService`.
- The dispatcher caps attempts by `app.notification.dispatch.maxMessagesPerRun` (default 100), checks a monotonic deadline between sends, and limits each query to the existing maximum batch of 50. Each Telegram HTTP attempt receives the remaining pass budget as a JDK request timeout; retries and backoff consume the same deadline. The dispatcher no longer reserves a fixed 63-second window, so shorter positive pass budgets still start a bounded attempt. Scheduling uses a two-thread pool so a slow dispatcher call cannot occupy the polling scheduler thread.
- Poll duration is recorded by the existing `loltracker.poll.duration` timer. The new `loltracker.outbox.oldest_retryable_age.seconds` gauge reports the age of the oldest PENDING or FAILED notification awaiting retry; pending/failed counts remain available.
- Retry/backoff and outbox persistence remain delegated to `NotificationDeliveryRecorder`. No claim is made for exactly-once delivery.

Independent review repair evidence: a 600-character fake 429 response is now persisted and reloaded with the rate-limit prefix intact and `last_error` at or below its 500-character column; the bulk cooldown is verified on a second distinct tracked match. The dispatcher stops the pass after any per-player exception so a partial result cannot allow later players to exceed `maxMessagesPerRun`. The 100-test Java 17 focused run includes this persistence regression and the dispatcher stop test.

Deadline semantics: `HttpClientConfig` applies 10-second connect and read timeouts by default for ordinary requests; dispatcher sends use a JDK `HttpRequest` timeout derived from the remaining monotonic budget. `TelegramNotifier` allows three attempts with a 1-second incremental retry backoff when the shared deadline permits, and reuses one thread-safe bounded `HttpClient` rather than creating one per retry. A deterministic localhost fixture that sends bytes every 100 ms confirms the 300 ms request deadline still terminates a trickling response. Database queries, message construction, and framework scheduling are not forcibly interrupted, so the configured duration bounds Telegram request/retry work rather than every instruction in the pass.

The coordinated slow-send integration test blocks the fake Telegram call in the dispatcher, runs another poll to completion while delivery is still blocked, verifies the outbox remains PENDING, then releases the send and verifies SENT. Polling continues to use its existing local guard and database lease; no row-lock claim is made for `PollRunService`/`PollRunRepository` in this change. The rejected agent run produced 47 integration failures after replacing `PollingService`; after restoring it and keeping only the outbox separation, the focused tests and full non-Docker suite passed.

Additional current evidence: the focused 429 lifecycle test persists `Retry-After`, refuses early retry, and delivers after the stored deadline; the dispatcher also rejects overlapping local runs. Full verification remains incomplete because PostgreSQL integration tests are skipped.
